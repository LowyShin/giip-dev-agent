# 요청 해석 검증 (Request Comprehension)

Paperthin의 핵심 검증 아이디어를 GIIP PDCA 흐름에 맞게 통합한다.

## 핵심 규칙
1. 작업 시작 전 사용자 요청을 내부적으로 재해석하고, 아래와 대조한다.
   - 현재 대화 맥락
   - 프로젝트 문서
   - `.agent/rules/` 규칙
2. 문맥으로 충분히 판단 가능하면 즉시 진행한다.
3. 결과가 달라지는 **모호성만** 한 번에 **한 가지씩** 질문한다.
4. 대규모 작업은 해석 결과를 아래 형식으로 기록한다.
   - `understood as: <reinterpreted requirements>` 형식을 기본으로 사용한다.
   - 한국어 문맥에서는 동등하게 `이해된 내용: <재해석된 요구사항>`도 허용한다.

## 사실 검증 규칙
- 외부 사양/API/라이선스/가격/보안 기준/클라우드 정보는
  - 공식 문서 URL, 또는
  - 실제 실행 로그/결과
  를 근거로 확인한다.
- 검증되지 않은 정보는 사실처럼 단정하지 않고 `추정`으로 명시한다.

## 기록 위치 (권장)
- Plan/Design/Report 등 PDCA 산출물의 "가정/해석" 섹션
- 대화 내 진행 보고

## Why
- 초기 해석 오류를 줄이고, 대규모 작업에서 요구사항 드리프트를 방지한다.
- 검증 근거를 남겨 재현 가능성과 책임성을 높인다.

## Paperthin readchk + aim 통합 (giip-fde-agent용)

### 요청을 받았을 때
- 문맥으로 목적이 명확하면 다시 묻지 않는다.
- 파일, URL, 로그, 코드, 데이터가 전달되면 현재 대화와 프로젝트 목적을 이용해 가장 합리적인 작업 목적을 먼저 추론한다.
- "무엇을 해드릴까요?" 같은 일반적인 되묻기를 하지 않는다.
- 결과가 크게 달라지는 실제 모호성이 있을 때만 질문한다.
- 모호성이 여러 개면 가장 중요한 한 가지부터 처리한다.

### 복잡한 작업
복잡한 작업 시작 시 내부적으로 다음을 구분한다.
- 실제 목표
- 사용자가 제시한 구현 방식
- 필수 제약
- 선택 가능한 구현 세부사항

사용자가 구현 방식을 명시적으로 강제하지 않은 경우 구현 방식은 목표와 동일시하지 않는다.
